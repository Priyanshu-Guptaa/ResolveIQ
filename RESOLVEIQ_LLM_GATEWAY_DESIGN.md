# ResolveIQ LLM Gateway / AI Answer Engine — Architecture & Data Flow

**Status: design only. No code written. Grounded in the actual repository as of 2026-08-13 (all Phase 1 Context Dimensions work already in place, tested, uncommitted, awaiting your approval to commit).**

---

## 0. What this changes about ResolveIQ, stated plainly

Every prior design document in this project (the original Chat Assistant assessment, this whole Phase 1 build) was explicit: **zero LLM anywhere in the runtime**, fully deterministic, fully on-prem. This request is a real, deliberate reversal of that specific constraint — not of the retrieval/ranking/grounding work itself, which stays exactly as built. I want that named up front rather than glossed over: approving this design means ResolveIQ's answer text will, for the first time, be generated by a third-party-hosted model, and a bounded amount of retrieved evidence will leave the local network per request. Everything in this document is built to make that boundary as narrow, auditable, and reversible as possible — but it is a real boundary that didn't exist before.

---

## 1. What ResolveIQ already provides (the retrieval/grounding layer, unchanged)

Grounded in the actual code, current as of this session's Phase 1 work:

- **`RecommendationEngine.generate()`** (`app/engines/recommendation/engine.py`) already produces an `InvestigationStrategy` — the single orchestrated object this whole design builds on top of, not around. It already contains, per investigation: `historical_investigations` (top-k, applicability-reranked `KnowledgeMatch` list), `known_bugs`, `documentation`, `ordered_log_collection` (`RecommendedLogCollectionItem`, each with a real `explanation` and `match_reason`), `suggested_sql` (`SuggestedSqlItem`, real governed `QueryTemplate`s), `matched_component` (`MatchedComponent`), `tfs_matches`/`wiki_matches` (`ExternalKnowledgeResult`, live TFS/Confluence), and `recommended_solution` (`RecommendedSolution` — the existing, deterministic, template-built "likely issue / rationale / what to check / recommended resolution / confidence / insufficient_evidence / source flags" object described in `app/domain/recommendation.py`).
- **`ApplicabilityRanker`** (`app/engines/knowledge/applicability.py`, built this phase) already re-ranks local search results by real Customer/Region/Technology applicability before anything is truncated to top-k — this is the "customer, region, product, technology... applicability" step requirement 4 asks for; it already runs, upstream of everything in this document.
- **`ExternalKnowledgeService`** (`app/engines/external_knowledge/`) already does live, scoped, cached, timeout-bounded TFS/Wiki search with a deterministic re-ranker (`ranking.py`) — the closest existing precedent in this codebase for "call an external system per-request, degrade gracefully, never block the rest of the answer."
- **`SqlLibraryEngine`**, **`ProductIntelligenceEngine`** (Component Registry) — already the source of the SQL and component evidence.
- **Not yet built**: Release Notes (no domain model exists — flagged in the original Chat Assistant assessment, still true), Resolution Provenance (`Confirmed`/`Likely`/`Possible`/`Unknown` tiering — designed conceptually in that same assessment, never implemented; `RecommendedSolution.confidence` today is only `"High"/"Medium"/"Low"/"Insufficient"`, not the 4-tier provenance model). Both are relevant to this design and called out below.

**The core design decision this document makes**: the LLM Gateway does not retrieve anything itself. It is purely a *consumer* of `InvestigationStrategy` (or an equivalent built for a standalone chat question, once that exists) plus a thin packaging/prompting/validation layer. This is the single most important property of the design — it's what makes requirements 11 and 12 (no KB duplication, no bulk data transfer) structurally true rather than a policy you have to trust.

## 2. New components

### 2.1 `GroundedContextPackage` (new domain model, `app/domain/answer_engine.py`)

The *only* thing that ever leaves the network. Built entirely from data `InvestigationStrategy` already computed — never a second retrieval pass, never a raw DB query.

```
GroundedContextPackage:
  question: str                        # the user's natural-language question, verbatim
  investigation_context: ContextSummary  # customer/region/product/version/technology/component,
                                          # already-resolved names only (never raw free text the
                                          # user typed elsewhere) -- reuses RetrievalContext (Part D
                                          # applicability work) + MatchedComponent
  evidence: list[EvidenceItem]          # bounded, ranked, deduplicated -- see §2.2
  insufficient_evidence: bool           # copied directly from RecommendedSolution -- see §3
  package_id: str                       # for audit log correlation (§6)
  built_at: datetime

EvidenceItem:
  source_type: Literal["historical_investigation","known_bug","documentation",
                        "tfs_case","wiki_page","sql_template","log_collection_step",
                        "component_profile"]
  source_id: str                        # the REAL id from the originating table/system --
                                          # this is what makes provenance traceable (req 9)
  title: str
  snippet: str                          # already-capped text ResolveIQ already produces
                                          # (KnowledgeMatch.snippet, TfsCase.description_text,
                                          # WikiPage.excerpt, ...) -- never re-fetched or expanded
  relevance_score: float                # the real, already-computed score (applicability-adjusted
                                          # where applicable)
  match_reason: str                     # the real, already-computed explanation ResolveIQ already
                                          # generates for every one of these object types today
  url: str | None                       # deep link back to the source system, when one exists
                                          # (TFS/Wiki already carry this)
```

### 2.2 Evidence selection budget (requirement 12, made concrete)

A fixed, small per-category cap applied *after* all existing ranking/applicability logic has already run — this step only truncates further, it introduces no new ranking:

| Category | Cap | Existing source |
|---|---|---|
| Historical investigations | 3 | `InvestigationStrategy.historical_investigations[:3]` |
| Known bugs | 3 | `.known_bugs[:3]` |
| Documentation | 3 | `.documentation[:3]` |
| TFS cases | 3 | `.tfs_matches.matches[:3]` |
| Wiki pages | 3 | `.wiki_matches.matches[:3]` |
| Log collection steps | 5 | `.ordered_log_collection[:5]` (already itself capped) |
| SQL templates | 3 | `.suggested_sql[:3]` |
| Component profile | 1, summary only | `.matched_component` → a short summary (responsibilities + typical_failures only, never the full graph of related_components/message_flows/etc.) |

Every snippet is already capped by existing code (`_MAX_SNIPPET_CHARS = 600` and equivalents) — this design adds one more ceiling: a **total package size budget** (proposed: ~6,000 characters, comfortably inside any current-generation model's context window with room for the system prompt and response). If the ranked evidence still exceeds it, items are dropped lowest-score-first per category, never truncated mid-item (a partial SQL query or partial log path is worse than one fewer example). The exact count/size is deliberately kept as one review-adjustable configuration, not a redesign parameter.

### 2.3 `LLMProvider` — provider-independent interface (requirement 10)

```python
class LLMRequest(BaseModel):
    system_prompt: str
    context_package: GroundedContextPackage
    max_output_tokens: int = 1500

class LLMResponse(BaseModel):
    raw_text: str
    provider_name: str
    model_name: str
    latency_ms: int
    finish_reason: str

class LLMProvider(Protocol):
    def is_configured(self) -> bool: ...
    def generate(self, request: LLMRequest) -> LLMResponse: ...
```

Same Protocol-plus-implementation shape as every external dependency already in this codebase (`EmbeddingProvider`, `TfsConnector`, `WikiConnector`, `LogParser`). First concrete implementation: `AzureOpenAIProvider` (or `AzureAIFoundryProvider`, depending on which Azure product line your enterprise Copilot license actually is — this needs your confirmation, see §8). Auth mirrors the two patterns TFS/Wiki already established in this codebase: Azure AD / Entra ID token (enterprise SSO, the NTLM/SSPI-equivalent — preferred for a domain-joined environment) or an API key read from environment/`.env`, never source or database (same `Settings` discipline as `tfs_base_url`/`wiki_api_token` today). A second provider (a different model, or a fully local model later) is a second class implementing the same three methods — nothing else in the system changes.

### 2.4 `AnswerEngine` (new, `app/engines/answer_engine/engine.py`)

The orchestrator. Takes an already-computed `InvestigationStrategy` (or the equivalent for a standalone question — see §7) plus the user's question, and:

1. Builds the `GroundedContextPackage` (§2.1–2.2) — pure packaging, no new retrieval.
2. Builds the system prompt (§3) — the same prompt every time, not per-question, so its behavior is auditable and testable independent of any one answer.
3. Calls `LLMProvider.generate()` — with the existing `ExternalKnowledgeService` pattern for graceful degradation: a timeout, a short in-memory cache keyed on the context package's content hash (repeat questions in a short window don't re-spend a call), and `available=False` on any failure — **the deterministic `RecommendedSolution` this system already produces is always the fallback, never a blank screen**.
4. Validates the response (§4) before it's ever shown.
5. Returns a `GroundedAnswer` (§5) — never the raw LLM text directly.

This whole engine is optional and additive: nothing in `RecommendationEngine`/`InvestigationStrategy`/Investigation Workspace changes. A build with `llm_gateway_enabled=false` (or no provider configured) is identical to today's ResolveIQ.

## 3. System prompt discipline (requirement 7/8)

The system prompt is not written per-request — one fixed, versioned prompt, so its rules are testable and auditable independent of any specific answer. Its non-negotiable contents:

- The model is given **only** the `GroundedContextPackage` — told explicitly it has no other knowledge of this organization's systems, customers, or history, and must not use general knowledge to fill gaps.
- It must structure its answer into exactly the sections requirement 7 lists (Problem interpretation / Likely root cause / Why / Recommended logs / SQL / Recommended resolution / Validation steps / Supporting references / Confidence) — **and must omit any section it cannot support from the given evidence**, not fill it with a plausible-sounding guess.
- Every factual claim beyond restating the question must carry an inline citation to one of the `source_id`s it was given (e.g. `[HI-a19f...]`, `[TFS-2467475]`) — no citation, no claim.
- If `context_package.insufficient_evidence` is `True`, or the evidence provided doesn't actually support a root cause/resolution, it must say so explicitly in those sections rather than omit them silently — matching the existing `RecommendedSolution.insufficient_evidence` contract this system already enforces deterministically today.
- Confidence must be stated as one of exactly `Confirmed` / `Likely` / `Possible` / `Unknown` (see §5.1) — never a free-floating percentage or the model's own self-assessed certainty.
- It must never suggest running a destructive SQL statement — every `SuggestedSqlItem` given to it is already read-only by construction (SQL Studio's existing scope, per `app/domain/sql_studio.py`'s own docstring: execution against a live database is explicitly out of scope), but the prompt states this constraint explicitly too, as defense in depth.

## 4. Response validation — the programmatic safety net (requirement 8, made real rather than aspirational)

A prompt is an instruction, not a guarantee. Every `GroundedAnswer` is checked before display:

1. **Citation verification**: every `[source_id]` the model cited is checked against the actual `source_id`s in the `GroundedContextPackage` that was sent. Any citation to an id that was never given is a fabricated reference — the offending claim is stripped (not silently kept), and the answer is flagged `citation_integrity: "flagged"` for visibility.
2. **Insufficient-evidence enforcement**: if `context_package.insufficient_evidence` was `True`, the response is scanned for a confident-sounding "Recommended resolution" section; if one is present despite no supporting evidence being given, the whole answer is rejected and replaced with the existing deterministic `RecommendedSolution` fallback (§2.4 step 3) — never shown to the engineer as if it were the LLM's word.
3. **No destructive SQL**: any SQL the model's answer contains beyond what was in the given `SuggestedSqlItem`s (i.e., anything it wrote itself rather than quoted) is stripped from the rendered answer entirely — only the exact, already-governed SQL text ResolveIQ supplied is ever shown as executable.

This is the same discipline `_synthesize_recommendation()` already applies deterministically today (§1) — this section is what makes that discipline survive contact with a component that isn't deterministic.

## 5. `GroundedAnswer` — the structured output (requirement 7)

```
GroundedAnswer:
  question: str
  problem_interpretation: str | None
  likely_root_cause: str | None
  why: str | None                        # the model's grounded explanation, citation-bearing
  recommended_logs: list[EvidenceRef]     # references back into context_package.evidence,
                                           # never re-stated/re-invented text
  recommended_sql: list[EvidenceRef]
  recommended_resolution: str | None
  validation_steps: list[str]
  supporting_references: list[EvidenceRef]  # historical/TFS/Wiki citations actually used
  confidence: ResolutionProvenance         # see 5.1
  insufficient_evidence: bool
  citation_integrity: Literal["ok","flagged"]
  provider_name: str
  package_id: str                         # ties back to the audit log entry, §6
```

### 5.1 `ResolutionProvenance` — reusing, not reinventing, the design already approved

The original Chat Assistant assessment already specified this exact four-tier model (`Confirmed`/`Likely`/`Possible`/`Unknown`) and the exact rule for `Confirmed` — cross-source correlation or explicit admin verification, **never** score alone. That work was designed but never implemented (it was the next planned phase before this request arrived). This design reuses it rather than inventing a second confidence scheme:

- **Confirmed**: only when the underlying evidence already meets that bar deterministically *before* the LLM ever sees it — a correlated TFS/local match (the existing `correlated_local`/`correlated_match` logic in `_synthesize_recommendation`) or an admin-set verified flag (not yet built, same as before). The LLM is never the one deciding something is Confirmed; it can only report a Confirmed tag that ResolveIQ already computed and put in the context package.
- **Likely**: a single strong source (High-confidence TFS/Wiki match, or a historical investigation above the similarity threshold) — the LLM may state this when the evidence given supports it.
- **Possible**: weaker/partial evidence — entity heuristics, Medium/Low external matches.
- **Unknown**: `insufficient_evidence = True` — the LLM states this and stops, per §3/§4.

This is the one place this design proposes adding a small amount of real logic that doesn't already exist: **the confidence tier is computed by ResolveIQ from the context package's own evidence quality, included in what's sent to the LLM as a hard ceiling ("you may state at most Likely for this answer"), and re-checked in validation (§4) rather than trusted from the model's own output.** The LLM explains the "why," it doesn't decide the tier.

## 6. Data flow

```
1. Engineer asks a question (Investigation Workspace or, later, Chat)
        |
2. Existing RecommendationEngine.generate() runs exactly as it does today
   -- local semantic search, applicability ranking, TFS/Wiki live search,
      log/SQL/component matching -- ALL LOCAL, unchanged
        |
3. InvestigationStrategy (already fully computed, already the API's
   existing response shape)
        |
4. AnswerEngine builds a GroundedContextPackage: bounded, capped,
   ranked evidence only (Part 2.1/2.2) -- STILL ENTIRELY LOCAL
        |
5. [NETWORK BOUNDARY -- the only place data leaves the org]
   AnswerEngine -> LLMProvider.generate(system_prompt + GroundedContextPackage
   + question) -> configured LLM endpoint (HTTPS, authenticated)
        |
6. LLM returns structured text
        |
7. [NETWORK BOUNDARY -- response returns]
        |
8. AnswerEngine validates (Part 4) -> GroundedAnswer
        |
9. Audit log entry written LOCALLY: package_id, what was sent (full
   context package), what came back (raw + validated), timestamp,
   engineer id if available -- never sent anywhere itself
        |
10. Rendered to the engineer, always with a visible "Sources" section
    resolving every EvidenceRef back to the real ResolveIQ record
    (existing detail views: Historical Investigation, Known Bug,
    Documentation, SQL Studio, TFS/Wiki deep links -- all already exist)
```

## 7. Security / data-flow assessment (requirement 13)

**Leaves the network, per request, only when the LLM Gateway is enabled and a question is asked:**
- The assembled `GroundedContextPackage` — bounded snippets (≤~6,000 characters total, per §2.2), never full documents, never raw database rows, never the full TFS/Wiki corpus.
- The engineer's typed question.
- Nothing else. No embeddings, no ChromaDB content, no SQLite dump, no credentials.

**Never leaves the network:**
- The vector index, the embedding model, SQLite, ChromaDB, uploaded document originals, TFS/Wiki credentials (NTLM identity / PAT), the full text of any document beyond what's in the sent snippets.
- All existing retrieval/ranking/classification work — unchanged, still 100% local.

**New risk this design introduces, and the mitigations proposed:**
- **Sensitive content in a snippet reaching the LLM provider.** The credential-file incident from earlier this session (a real plaintext-password document caught by hand before import) is exactly the failure mode to worry about here, at a different layer: even correctly-imported, non-credential content could still contain customer-sensitive details an org doesn't want leaving its boundary. Recommendation: a lightweight secret/PII-pattern scan (same regex-based approach already recommended and not yet built for ingestion) applied to the assembled context package immediately before the network call — block and log, don't silently strip, on a match.
- **Provider data retention.** Whatever contractual/technical guarantee your Azure OpenAI/Copilot enterprise agreement provides (no training on submitted data, retention window, region) needs to be confirmed and documented here before this goes live — this is a legal/procurement question, not an engineering one, and this document can't answer it for you (§8).
- **Prompt injection via retrieved evidence.** A wiki page or TFS case description is, ultimately, untrusted text that gets placed into the LLM's context — same category of risk as any RAG system. Mitigation: the citation-verification step (§4) means even a successfully-injected instruction can't cause the model to cite a source that wasn't given, and the system prompt's structural constraints limit what a hijacked response could actually do (it can't execute anything — this whole system only ever renders text and pre-existing, already-governed SQL).
- **No new attack surface for write access.** The LLM never gets any ability to modify ResolveIQ data, execute SQL, or call any other system — output-only, text-only.
- **Audit trail.** Every request/response pair logged locally (§6, step 9) — this is genuinely new (nothing in ResolveIQ today logs "what was shown to a human" at this granularity) and is the direct enabler of any future compliance review of what left the building.
- **Kill switch.** `llm_gateway_enabled: bool = False` default in `Settings`, mirroring `external_knowledge_enabled`'s existing exact pattern — a fresh checkout or an org that decides against this entirely runs with zero behavior change and zero code path exercised.

## 8. Open questions before implementation

1. **Which Azure product, specifically?** "Azure/Copilot" spans several distinct offerings (Azure OpenAI Service in your own tenant, Microsoft Copilot Studio, Microsoft 365 Copilot extensibility) with materially different auth models, data-handling terms, and integration surfaces. I need to know which one your organization has actually licensed before the `AzureOpenAIProvider` implementation (not this design) can be written correctly.
2. **Data residency / retention confirmation** — see §7. I can build the *mechanism* (the narrow context package, the kill switch, the audit log) but not confirm your organization's actual contractual guarantee.
3. **Context package size budget** — is ~6,000 characters the right ceiling, or does your licensed model/tier support (and would you want) a larger window for richer evidence?
4. **Human-in-the-loop** — does an engineer need to explicitly acknowledge "this section was AI-generated, verify before acting" per answer, or is the citation/provenance display sufficient? This affects the UI, not this backend design, but worth deciding now.
5. **Standalone-question chat vs. Investigation-scoped only for v1** — this design works identically for both (§2.4 takes an `InvestigationStrategy`-shaped input either way), but building the standalone-question path means finishing the Chat Assistant's own context-resolution work (asking "what product/customer is this about" when unstated) — do you want v1 scoped to *inside an open investigation only* (simpler, InvestigationStrategy already exists) with standalone chat as a deliberate v2?
6. **Resolution Provenance** — should I build the real `Confirmed`/`Likely`/`Possible`/`Unknown` tiering (§5.1) as its own, LLM-independent phase first (as originally planned before this request), so it's tested on its own before the LLM ever depends on it? I'd recommend yes.
